# 設計

かさねいろの設計原則と、主要な設計判断とその理由、いま決めないことの一覧。**「なぜそうしたか」の正典**。仕組みの具体(テクスチャ・binding・パス順・モジュール)は [architecture.md](architecture.md)、要件は [requirements.md](requirements.md)、現在地は [status.md](status.md)、要素技術の調査は [note/00-overview.md](note/00-overview.md) を参照。

## 1. 設計原則

**試行錯誤の速度を最優先する。** このプロジェクトの品質はアルゴリズムの選択ではなく**パラメータ調整の反復回数**で決まる([note/01](note/01-fluid-simulation.md) §1「パラメータ調整が見た目を大きく左右する」)。そこで次の2点を構造として組み込む:

1. **シミュレーション本体より先に調整ループを回す道具を持つ** — ホットリロード・パラメータパネル・デバッグ表示・ストローク再生(装備 H1〜H6、§2)
2. **完了条件は「目で見て判定できる体験」で定義する** — 数値目標ではなく「2色が馴染んで綺麗なグラデーションになるか」のような体感チェックにする。判定できないものは作りすぎのサイン。e2e テストもこの方針で、数値を固定せず体験が壊れていないかだけを見る

この原則から出てくる具体的な選択:

- 既定のキャンバスは軽い 512²。重いサイズ(2048²)は描くとき用で、調整は軽いサイズで回す
- 構造の抽象化は「必要になってから、必要な分だけ」。trait 化・include 機構・crate 分割などは §4 の再検討トリガーが来るまでやらない
- 物理的な正しさより、スライダーで効きが読めることを優先する。同じ現象を複数のパラメータで表すより、一次原理(例: 水の毛細管拡散)1つに寄せて効きを単純にする([note/05](note/05-wet-spreading.md) §0)

## 2. 試行錯誤ループ(装備 H1〜H6)

理想の調整ループは以下で、**1周を数秒以内**に収める:

```
パラメータを1つ動かす(スライダー or WGSL編集)
  → 同じストロークが自動で再描画される(ストローク再生)
  → 前の結果と見比べる(スナップショット比較)
  → 良ければプリセット保存、悪ければ戻す
※ どこにも再コンパイル・再起動・手描きのやり直しが入らない
```

これを支える6つの装備(実装の現在地は [status.md](status.md) §3、仕組みは [architecture.md](architecture.md) §11):

| # | 装備 | 内容 | 効果 |
|---|---|---|---|
| H1 | **WGSLホットリロード** | シェーダーをファイルから実行時ロードし、保存で即再コンパイル。コンパイルエラーは画面にオーバーレイ表示し、直前の正常なパイプラインで続行(クラッシュさせない) | シェーダー編集で Rust 再コンパイル不要に。**調整作業の大半をカバー** |
| H2 | **パラメータパネル** | 全シミュレーションパラメータを単一の `SimParams` 構造体に集約し、そのまま uniform buffer として GPU へ。egui スライダーは構造体のフィールドと1対1。**パラメータ追加 = フィールド1行+スライダー1行+WGSL1行**の定型作業にする | スライダーはリアルタイム反映 |
| H3 | **プリセット保存/読込** | `SimParams` を JSON で `assets/presets/` に保存・読込。**プリセットは git にコミットする**(「昨日の良かった設定」を失わないため) | 試行錯誤の成果が蓄積される。悪化したら即戻せる |
| H4 | **デバッグ表示切替** | 水量 / 速度場 / 浮遊顔料 / 沈着顔料 / 紙ハイト / 湿りオーバーレイ / アクティブタイルなどを可視化する表示モード | 「なぜ滲まないのか」を見て診断できる。シェーダーデバッグの難しさへの最大の対策 |
| H5 | **ストローク記録・再生** | 入力イベント列(位置・筆圧・時刻)を JSON で記録し、キャンバスをリセットして同一ストロークを再描画。代表的なテストストロークをリポジトリに同梱 | **同一入力での A/B 比較**。「手描きし直したら再現しない」を排除。e2e テストの入力にもなる |
| H6 | **シミュレーション制御** | 一時停止 / 1ステップ実行 / 速度倍率 / キャンバスリセット + PNG スナップショット | にじみの進行をコマ送りで観察。before/after の証拠を残す |

### 検証の分担(CPU 参照実装はやりすぎない)

全パイプラインの CPU 二重実装は過剰なので、検証手段を対象ごとに分ける:

| 対象 | 検証手段 | 理由 |
|---|---|---|
| KM 合成と K,S 逆算 | CPU 参照実装 + `cargo test`(`crates/km`)で WGSL と突き合わせる | 純関数で、数値の正しさに意味がある |
| 流体本体 | デバッグ表示(H4)+ストローク再生(H5)で目で診断。e2e は体験の帯だけ見る | 数値の正しさより見た目が大事。数値を固定すると調整の足かせになる |
| WGSL 全体 | naga でコンパイル可能性、`SimParams` の Rust / WGSL レイアウト一致を機械検査 | 実行時ロードなので `cargo build` では壊れた WGSL を検出できず、uniform は生バイトで渡すのでずれてもコンパイルが通る |

GPU の数値が疑わしくなったカーネルが出たら、そのカーネル単位で CPU 参照実装を後追いで足す。

## 3. 主要な設計判断

### 3.1 プロジェクト構成

- **workspace を km / pigment / paint-core の3 crate + ルートの kasaneiro crate に分ける**。目的は2つ:
  - **mixbox(CC BY-NC)の隔離を依存グラフで強制する** — mixbox に依存するのは `crates/pigment` だけ。`cargo tree` で機械的に確かめられ、商用化時に自作スペクトラル WGM へ差し替える範囲がこの crate に閉じる
  - **CPU 純粋部を wgpu 抜きで数秒でテストできるようにする** — km / pigment / paint-core は wgpu をリンクしない
- **ルート crate は lib + 起動だけの bin**。e2e テストがウィンドウなしで同じモジュールを駆動できるようにするため
- **依存クレートは egui の対応バージョンを起点にロックステップで固定**する(egui → egui-wgpu → wgpu → winit の順に合わせる。[note/04](note/04-platform-and-references.md) §1)
- **コンパイル時間対策**: 依存クレートだけ opt-level 2、自前コードは opt-level 1。シミュレーションは GPU 側なので dev ビルドでも 60fps が出る
- **筆圧は winit / egui 標準の Touch イベントで取る**。octotablet はメッセージループのデッドロック([issue #18](https://github.com/Fuzzyzilla/octotablet/issues/18))で使わない

### 3.2 シェーダーとパラメータの置き場

- **WGSL は実行時ロード**(H1)。配布ビルド(feature `embed-assets`)だけ exe に埋め込む。埋め込むとホットリロードが無効になるので通常ビルドでは付けない
- **シミュレーションパラメータは `SimParams` 1つに集約**(H2)。プリセット・ストローク記録・作品保存がすべてこの構造体を丸ごと持てば済む
- **表示専用の値(パン・ズーム・回転)は `SimParams` に入れない**。別の uniform にして、プリセットやストローク記録を表示状態で汚さない
- **Rust と WGSL で共有する定数は Rust 側が唯一の正典**。`shader_prelude` が const を生成してシェーダーの先頭に連結するので、キャンバスサイズ依存の値(タイル数など)も WGSL にベタ書きしない
- **パス実行順はコードのハードコード(`encode_frame()`)が正典**。パイプラインの生成は表駆動(シェーダー追加 = 表に1行)にするが、実行順まで汎用化はしない(§4「パス実行の trait 抽象化」)

### 3.3 シミュレーションのモデル

- **流体は Curtis 1997 の簡略版 + 水の毛細管拡散**。速度更新 → 発散緩和 → 移流の骨格に、水量そのものが濡れた紙を伝って広がる拡散を足す。「置いたら馴染む」「広がる勢い」を別々の仕掛けで作らず、毛細管現象1つで説明する([note/05](note/05-wet-spreading.md))
- **状態は水・浮遊顔料・沈着顔料の3テクスチャ**で、顔料は rgba の4チャンネル=同時4顔料。浮遊は水と一緒に動き、沈着は紙に定着して動かない(Curtis の2層モデル)
- **ping-pong は3テクスチャまとめて単一の `current`** で管理する。パスごとに index を分けるより単純で、変更しないテクスチャを素通しするコストはアクティブタイルで濡れ面積比例に収まる
- **シミュは 1/60 秒の固定刻みで進め、フレームとは切り離す**。蒸発・拡散はステップ数で効くので、フレームごとに回すと高リフレッシュのモニタほど速く乾き、調整した乾き方・e2e・ストローク記録のテンポが機種をまたがない。経過時間を刻みに積み立て、記録再生も刻み単位にする。重いフレームで追いつこうとして悪循環に入らないよう1フレームの刻み数に上限を置き、超えた分は実時間より遅れることを許す
- **顔料の個性は ρ(沈みやすさ)/ ω(染みつき)/ γ(粒状感)/ μ(粒の細かさ)+色**。水彩絵具の個性(粒状化するウルトラマリン、染みつくフタロ、分離色)をこの4つで表す。全レイヤー共通の物性で、色だけがレイヤーごとに記録される(§3.5)

### 3.4 混色・発色(2段構え)

**層「内」の混色 = mixbox、層「間」の合成 = Kubelka-Munk** と役割を分ける。

- RGB 3ch の K,S で層内を混ぜると黄+青が濁り、mixbox を使う意味が消える。だから層内は mixbox の latent を線形混合して発色する
- 層の重なりは KM の反射率・透過率合成で光学的に重ねると「内側から光る」水彩らしい重なりになる。各層の R, T は、その層を白地・黒地に置いた mixbox 発色 R_w, R_b から `R = R_b`、`T² = (R_w−R_b)(1−R_b)` の閉じた形で導く(sinh/cosh が要らずオーバーフロー対策も不要)。この簡約が Curtis の一般式と一致することは `crates/km` のテストで担保する
- 「顔料ごとの K,S プリセット」は持たない。混色モデルを二重化しないため
- 顔料の色は CPU(`crates/pigment`)で latent にして uniform で渡し、GPU は latent の混合と latent→RGB 多項式だけを行う。mixbox の呼び出しが CPU の1か所に閉じる

### 3.5 乾燥とレイヤー

- **湿レイヤーは常に1枚、乾燥レイヤーは焼き込みで積む**。Curtis の glaze 列と同じ「レイヤー確定=乾燥」の構造で、要件の「レイヤー構造でいい」と一致する。焼き込みは一方通行で、乾燥レイヤーは再編集しない。中間操作として Fast Dry(焼かずに止める)と再湿潤(濡らし直す)を持つ
- **乾燥レイヤーは RGB に潰さず顔料濃度のまま保持する**。合成方式や表示を変えても latent から発色し直せる
- **乾かした瞬間のパレットをレイヤーごとに記録する**。顔料を後から編集しても乾いた層の色は変わらない。GPU 側の latent 枠は表示用のキャッシュで、名前・物性込みの正典は CPU 側(`GpuCanvas::layer_palettes`)に置く。これで同時4顔料の制約のまま、色数はレイヤーをまたいで実質無制限になる
- **乾燥レイヤーの枚数上限は、下の層を下地に焼き固めて逃がす**。上限を上げるだけでは壁が先に延びるだけで VRAM も増える。合成は紙から下の層へ順に積む逐次計算なので、下の N 枚の結果を新しい「紙」として固定すれば見た目を変えずに枠を空けられる。下地は合成キャッシュと同じ形式で乗算・KM の両方式ぶん持ち、合成方式の切り替えにも耐える。代わりに統合した層の並べ替え・表示切替・記録パレットは手放す(使い込みで下の層をいじる頻度は低い)。スロットは詰め直して「使用中 = 0..len、添字 = slot」の単純な不変条件を保つ
- **乾燥レイヤーの合成はキャッシュに焼いておく**。乾燥レイヤーは描いている間は変わらないので、毎フレーム発色するのは湿レイヤーだけにして、表示コストを乾燥レイヤーの枚数によらなくする
- **合成順は 紙 → 乾燥(下から)→ 湿 → 線画 → ハイライト で固定**。水彩は透明なので、線画を色の上に置いて困らない

### 3.6 線画とハイライト

- **ラスタの専用テクスチャに直描きし、流体を通さない**。下書き鉛筆・清書ペン・白ハイライトを独立に表示・消去できる
- **線画は多段 Undo/Redo、水彩は1段 undo**。線画は流体を通らないので、ストローク列(生ポインタ点+そのときの SimParams)から決定論的に引き直せる。水彩は流体の状態を丸ごと退避するしかないので、全面スナップショットの1段に留める
- **清書ペンの線を水の境界にする(透水率)**。ペン濃度から透水率を出して速度場と拡散の流束にだけ掛け、ブラシの直接注入には掛けない。線を跨いで塗れば越えられる=はみ出し防止であって塗り禁止ではない
- **ハイライトは不透明白で流体なし**。白は透明水彩では出せない(紙を残す)ので、最上段の別レイヤーとして扱う

### 3.7 計算範囲(アクティブタイル)

- **シミュレーションのコストを「紙の広さ」比例から「濡れ面積」比例にする**。2048² の「広い紙」を成り立たせる前提
- **タイル早期リターン方式**で ping-pong 構造を崩さない。タイル(16×16)ごとに 計算する / コピーだけする / 何もしない の3状態を毎フレーム決め、各パスはタイルの状態を見て早期 return する。代償として、何もしないワークグループも全面に起動される(乾いた紙でも残るコスト。[status.md](status.md) §1.4 の性能)
- **計算するタイルは「濡れマスク」ではなく「まだ動きうるか」で決める**。濡れマスクは湿った紙(次の水が伝う道)の意味を持つので蒸発では下ろさないが、水・速度・浮遊顔料がすべて 0 のセルは全パスで不動点になる。判定だけをそこへ寄せれば、シミュの結果を変えずに乾き切った領域を計算から外せる
- **ping-pong の2枚が一致しているタイルだけ書き込みを省く**。計算したタイルは次のフレームで一度コピーして2枚を揃える(dirty)。この不変条件は e2e が2枚を読み戻して検査する
- **`active_tiles=0` で全面計算に戻せる退避口**を残す。A/B と不具合の切り分けのため

### 3.8 キャンバスと入力

- **キャンバスは正方形のみ・サイズ可変(512 / 1024 / 2048)で、テクセル密度は据え置き**(=大きいサイズは「広い紙」)。ブラシ・にじみのテクセル単位のパラメータを再調整しなくて済む
- **サイズ変更は GPU 状態の丸ごと作り直し**。テクスチャ・タイルバッファ・bind group が全てサイズ依存なので、部分再構築より単純で安全
- **ストローク記録は splat 列ではなく補間前の生ポインタ入力**。再生時にブラシ半径などを変えて同じストロークで A/B 比較できる
- **入力と保存は trait / 1モジュールの境界で抽象化**しておく(`PointerSource`、作品のファイル入出力)。Web 版はやらないが、やるときに差し替える場所をここに限定する

### 3.9 保存

- **軽い設定は JSON、作品は独自バイナリ1ファイル**。プリセット・パレット・色・ストロークは git にコミットして差分を見たいので JSON。作品は数十 MB の生 f32 テクスチャを含むので、メタ JSON + 生ブロブの1ファイル(`works/*.kasane`、git 管理外)
- **作品は湿った状態ごと保存する**。描きかけをそのまま再開できる。線画の Undo 履歴はテクスチャがあれば絵は戻るので保存しない
- **作品ファイルはキャンバスサイズをまたいで持ち運べる**。読込時にサイズが違えば作り直してから復元する
- **省略できる状態はメタの省略時既定値で表し、識別子を上げずに済ませる**。下地はある作品だけ末尾にブロブを足し、メタの `has_base` は省略時 false にするので、下地のない作品はこれまでの並びのまま読み書きできる
- **リプレイ動画は外部の ffmpeg に生フレームを流して作る**。動画エンコーダのクレートを抱えるとコンパイル時間と配布物が重くなり、GIF は 256 色で水彩のグラデーションが縞になる。ffmpeg なら依存を増やさず H.264 の画質とサイズが得られる。代わりに ffmpeg の用意(PATH / exe 隣 / 環境変数)は使う人に任せる
- **動画は画面とは別のキャンバスで裏再生して撮る**。画面の描画を撮るとズーム・回転や UI 操作が混ざり、書き出し中に描けなくなる。headless 再生(e2e と同じ経路)なら1シミュレーションフレーム = 1動画フレームで取りこぼしがなく、記録時のテンポがそのまま動画の時間になる

## 4. 先送りする判断(いま決めないことを決める)

| 論点 | 当面の選択 | 再検討のトリガー |
|---|---|---|
| 混色ライブラリ | mixbox クレート(CC BY-NC)。呼び出しは `crates/pigment` に隔離 | 配布・商用化したくなったら自作スペクトラル WGM([note/02](note/02-pigment-mixing.md) §3)へ差し替え |
| 流体ソルバ | Curtis 簡略版(反復緩和)+**毛細管拡散**(水高さの拡散、[note/05](note/05-wet-spreading.md)) | 不安定なら Stam 化、にじみ境界の表情が足りなければ LBM(MoXi) |
| 紙の質感再現(シミュ側) | 既定オフ(paper_amp/gran/wet=0。機構・スライダーは残置) | しばらく使って不要が確定したら紙ハイト機構ごと削除。逆に粒状感が欲しくなったら値を戻すだけ |
| undo(湿レイヤー) | 1段のみ(全面スナップショット)。線画・ハイライトは多段 Undo/Redo(ストローク再生方式) | 水彩側も複数段が欲しくなったら。2048² ではタイル差分化が前提 |
| 線画 Undo の周期チェックポイント | なし(毎回全ストローク再ラスタライズ) | ストローク数が増えて Undo/Redo の再生が体感で遅くなったら(Kストロークごとにテクスチャ退避+差分再生) |
| 同時顔料数(4ch→8ch) | やらない(4ch のまま。色数はパレット・ライブラリ+レイヤーごとパレット記録で実質無制限) | **1つの湿レイヤー内で同時に5色以上を混ぜたくなったら**。やる場合: 浮遊/沈着/乾燥テクスチャを2枚組(2×vec4)にし顔料を触る全シェーダー(約8本)を拡張+ `max_storage_textures_per_shader_stage`(既定4→5必要)を eframe の WgpuConfiguration で引き上げ。512² なら性能余裕、実コストは binding 付け替えの手間 |
| スポイトの意味論 | 表示色を拾う | 「その点の顔料構成」を拾いたくなったら(混合物→単一スロットの写像が曖昧なので沼。表示色版で不満が出てから) |
