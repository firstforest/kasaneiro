**線画の消しゴムに描く太さとは別の太さを持たせる(2026-11-03)**: ユーザー要望「ペンと消しゴムで別のブラシサイズを保持するようにして」への対応。それまでは鉛筆・清書ペン・ハイライトの消しゴムが各レイヤーの描く太さを共用していた。案(線画レイヤーごと / 線画で1つ共通 / 水彩の「消す」も含めて分ける)を出し、ユーザーが「線画レイヤーごと」を選択した。`SimParams` に `pencil_eraser_radius`(16)・`pen_eraser_radius`(10)・`highlight_eraser_radius`(12)を足し、`SimParams::line_radius(line_mode, eraser)` で描く太さ / 消しゴムの太さを選ぶ。ライブ描画の補間間隔・カーソル表示・Ctrl+Alt+ドラッグ(`active_base_radius` / `adjust_active_radius`)、線画履歴の引き直し(`stroke_splats`、保存済みの line_mode / line_eraser から引く)、linesplat.wgsl の半径の選び方をこれに揃えた。「太さ」スライダーは線画パネル共通のヘッダへ移し、消しゴム中は「消しゴムの太さ」になる。水彩の「消す」は塗る筆の太さのまま。e2e_ui: `pen_eraser_keeps_own_radius`(4px のペン線を 10px の消しゴムで横切るとペン幅の外まで消え、消しゴムを外すとペンは細いまま、Undo → Redo で同じ消し跡)。SimParams は 67 フィールド+パディング1 = 272B。**SimParams のレイアウトが変わったので再ビルド・再起動が必要**。

**清書ペンの描き味: 手ぶれ補正・細い線・重ねた所の濃さ(2026-11-03、要目視確認)**: ユーザー要望「線画は書き味が一番。細かい線を描きやすくしたい。線を重ねて濃くなる感じも少し欲しい。下書きは今のままでよく、清書を改善したい」への対応。コードを読んで、細い線が描きにくい原因を2つ見つけた。①linesplat.wgsl のペンの分岐が、半径に掛けた筆圧の上からさらに `mix(0.5, 1, 筆圧)` を掛けていた(筆圧 0.3 で基準の約 0.2 倍)。②縁の遷移帯 `smoothstep(r−1, r)` が線の内側に寄っていて、半径 1px 前後の線がピクセル中心を外れて点線に欠けていた。筆圧は1回だけ掛け、縁を中心にした 1px の遷移帯にし、半径 0.7px 未満は細さの比で濃さを落とすようにした。手ぶれ補正は案(曲線補間+遅れて追う補正 / 曲線補間だけ / 補正だけ)、重ねの濃さは案(ストローク単位で重なる / 描くほど溜まる)を出し、ユーザーが「曲線補間+追従補正」「ストローク単位」を選択した。`paint_core::brush::LineSmoother`(指数移動平均 → centripetal Catmull-Rom)を清書ペンのライブ描画と線画履歴の引き直しの両方に通し、`pen_smooth`(既定 0.3)を `_pad` の位置に足した。重ねの濃さは、描き始めにペン層を `pen_base` へ複製し、`max(今の値, 下地 + 量×(1 − 下地))` で溜める(表示とストローク終了時の合成は変えずに済む)。重ねが見えるよう `pen_strength` の既定を 0.9 → 0.75 にした。e2e_ui: `pen_overlapping_strokes_darken`(交点が1本より濃く、1本の中の往復は濃くならない)・`pen_light_pressure_line_is_continuous`(筆圧 0.15 の線が途切れず濃さがそろう)・`pen_undo_redo_restores_same_lines`(元に戻す → やり直しで同じ線)。paint-core: `LineSmoother` の単体テスト3本。SimParams は 64 フィールド = 256B。**SimParams のレイアウトが変わったので再ビルド・再起動が必要**。要目視確認: status.md §1.6「清書ペンの描き味」。

**切れ込みの先端が光る点になるのを修正: 移流で乾いたセルを補間に混ぜない(2026-11-03、要目視確認)**: ユーザー報告(`--capture` の記録で、3色を重ねた溜まりの3か所が周りより明るく光る。塗り跡に乾いた紙の切れ込みが残った所の先端のすぐ内側、直径 8px ほど)。記録を headless で再生して再現し、仕組みを1つずつ止めると、流れ(`vel_max` = 0)を止めたときだけ3か所とも消えた。今日の変更(筆の勢いの3乗・弦の補正)より前の splat.wgsl でも出る。原因は advect.wgsl のバイリニア補間が乾いたタップ(水も浮遊顔料も 0)を混ぜていたこと: 取り込んだ分だけ水と色が消え、水は圧力と毛細管拡散で周りから戻るが顔料は戻らないので、乾いた紙に囲まれた所で色が抜け続ける。濡れたタップだけで重みを割り直す `bilinear_wet` にした(水と浮遊顔料を同じタップ・同じ重みで1回の読み込みで取る。濡れたタップが無ければ自セルの値)。調整パラメータは増やしていない。性能はほぼ同じ(2048² 全面計算 4.61 → 4.49 ms)。塗りの内側の光る円を画像全体で数えると、条件を変えた再生のどれでも4か所 → 1か所(残りは 1〜2px の水色の点で、修正前からある別の現象)。光る場所は流れのわずかな違いで移る(今日より前の splat.wgsl では別の場所が光る)ので、テストは決まった座標でなく画像全体で見る。e2e: `dark_pool_notches_do_not_glow`(記録 [dark-pool-notches.json](../assets/strokes/dark-pool-notches.json) を再生し、塗りの内側で周りより明るい所の最大が 0.03 未満。修正前は 0.045 で落ちる)。要目視確認: status.md §1.6「切れ込みの先端の光る点」。

**拭った筆の往復の境目に白い筋が出るのを修正: 筆の当たりを一様にし、弦の補正を入れる(2026-11-03、要目視確認)**: ユーザー報告「水が少ない筆の線を重ねると、線の周囲に白い枠のようなものが残る」。`--capture` の記録(拭った筆でジグザグの1ストローク)を headless で再生して再現した。筋は往復の縁どうしが並んだ所の幅 6〜8px の明るい帯。1 回なぞる間に紙のセルが splat に触れる回数は中心 8 回・縁 2〜4 回(弦の長さの効果)で、受け渡し(1 splat で差の 3 割)が縁で 5〜7 割までしか進まず、当たりも縁の外側 4 割が柔らかく減衰していた。満タンの筆は拡散で均されるが、拭った筆は紙の水が 0.2 ほどで毛細管拡散も顔料拡散もほぼ効かず、置いた形のまま固まる。溶かし戻し・エッジダークニング・アンチエイリアス・にじみ拡張・蒸発・流れ・顔料拡散・吸い取りを1つずつ止めても消えず、減らない筆(brush_hold = 0)でも出る(筆が乾いていくせいではない)。途中で「重ねた所が濃くなる」案(水と無関係に顔料が接触で移る、スライダー `brush_contact` / 定数 `CONTACT_TRANSFER`)を試したが、ユーザーから「調整パラメータを増やして複雑にするのは嫌」「必要最低限の複雑さで」と指示があり、Fable(claude-fable-5-1)に検討させた結果、接触転写は筋の原因に効かず既存 e2e 2 件(筆の濃さ)を落とすので外した。採ったのは、塗る筆の当たりを円の内側で一様・端 1px で切る形にし(`FOOTPRINT_RATIO` 0.648 → 1.25、`CROSS_RATIO` 1.6 → 2.0)、進行方向と直交する中心線からの距離 u で 1/√(1−(u/r)²)(上限 `CHORD_MAX` = 3)を掛ける弦の補正。調整パラメータは増やしていない。中心からの距離で掛けると splat の輪が縞に出たので直交する距離にした。結果: 拭った筆の1本の断面が平らになり(明度 0.809 で一定)、ジグザグの境目は往復の中心よりわずかに濃く、横切った所は 1 回だけの所より濃い。満タンの筆のジグザグはほぼ同じ。e2e: `wiped_brush_zigzag_has_no_white_seams`(往復の境目が往復の中心より 0.01 以上明るくない・横切った所が 1 回だけの所より 0.01 以上濃い)を追加。並列のワークスペース全体テストで `e2e_watercolor` が止まる(CPU を使い続け、メモリ 2GB 前後)ことが2回あった。直列(`--test-threads=1`)では 17 秒で通る。原因は未調査。要目視確認: status.md §1.6「拭う」。

**解析用キャプチャ `--capture`(2026-11-03)**: ユーザー要望「オプション付きで起動すると、解析に必要なログやストローク情報を一時ファイルとして記録し、終了時に画面のスクショも保存する」。拭った筆で線を重ねると白い枠が残るという報告を headless で再現しきれず、実際の操作を手動のストローク記録で取ってもらう手間を減らすため。範囲(基本 / 基本+終了時の全状態 / 操作ごと再現できる記録)と保存先(OS の一時フォルダ / リポジトリ内 target/capture)を出し、ユーザーが「基本+終了時の全状態」「target/capture」を選択。`src/capture.rs` に置き、アプリは記録の差し込み口(H5 の Recorder と並べて回す)・毎フレームの観測・閉じる要求の横取りだけを持つ。キャプチャの再生で、headless の表示先(sRGB)とアプリ(非 sRGB)で同じ絵の写りが違うことに気づいた(status.md §1.5 に記載。直していない)。e2e: `capture_writes_session_on_close`(描いて閉じる要求を送ると、閉じる前に記録一式を書いてから閉じる)。

**拭う: 水の少ない筆を作れるように(2026-11-03、要目視確認)**: ユーザー要望「水が少ない筆を作れるようにしたい」。色・水・スポイトはどれも筆の水を満タンにするので、水の少ない筆は描いて減らす以外に作れなかった。案(拭うボタン / 含ませる水のスライダー / 両方)、水を減らしたときの濃さ(顔料を残して濃くする / 色水ごと抜く)、かすれ(紙の凸部だけに乗る)を入れるかを出し、ユーザーが「拭うボタン・顔料を残して濃くする・かすれは今回入れない」を選択。ツールバーの水と洗うの間に「拭う」を置き、押した瞬間に水を半分(`WIPE_KEEP`)、押している間は時定数 0.5 秒(`WIPE_TAU`)で水だけ抜け、満タンの 1 割(`WIPE_MIN_WATER`)で止まる。穂先と腹の両方にかけ、自動補充の戻り先にもなる。出る水 × 濃さ = 置く顔料なので、乾いた紙に置く顔料は満タンの筆とほぼ同じで、紙を濡らす水だけが減る(水 0.3 で芯の明度 0.840 → 0.842、中心から 12px の縁 0.841 → 0.894)。拭った筆の線にストロークの1歩ごとの粒の列が出た(芯の明度の 15px 移動平均からの揺れ RMS 0.0077、満タンは 0.0009)。筆の勢いを 0 にすると 0.0012 に下がったので、2026-11-02 の「洗った筆の段々」と同じく、少ない水が勢いを持って1歩ごとの濡れ縁へ寄るのが原因。出る水の速さを穂先の濡れ具合に比例 → 2乗(0.0021、うっすら残る)→ 3乗(0.0013)と試して3乗にした(満タンの筆の勢いは変わらない)。e2e: `wiped_brush_paints_without_spreading`(芯の濃さの差 < 0.03、縁が 0.02 以上明るい、揺れ RMS < 0.0025)を追加、paint-core に `wipe_removes_water_and_keeps_pigment`。要目視確認: status.md §1.6「拭う」。

**色の縁のアンチエイリアス(2026-11-03、要目視確認)**: ユーザー要望「色のレイヤーでジャギジャギになるのをアンチエイリアスできないか。今の水彩表現をこわさない方法で」への対応。e2e の出力とユーザーの記録 `test.json` の再生画像で縁を拡大すると、1テクセルを境に「色あり」と「紙の白」が切り替わる階段になっていた。濡れマスク(`splat.wgsl` の `dist < radius` で 1)が二値で、水と顔料がその内側だけで均されるため。案として、A 表示で輪郭を描き直す / B 縁のテクセルに覆いの割合を入れる(湿レイヤーは表示、乾いた層は焼き込み)/ C 濡れマスクを小数にしてシミュ側で直す(水彩の挙動が変わるので非推奨)を出し、ユーザーが B を選択した。common.wgsl に `edge_aa_conc` を置いた。「色がある/ない」を3×3のテント重みでならし、その Sobel 勾配から縁までの距離を出して、テクセルの覆いの割合にする。display.wgsl の `wet_conc_aa` が湿レイヤーに、bake.wgsl が焼き込む濃度に掛ける。`edge_aa`(既定 1、0 で従来どおり)を追加した。同じコードで `edge_aa` 0 / 1 を比べると、`test.json` の濃い斜めの縁では階段の角に中間のテクセルが入ってなめらかになり、塗りの内側は変わらなかった。e2e の他のストロークは縁へ向かって薄くなるので、差は最大 11/255。e2e_watercolor は閾値を変えずに全件パスした。表示時間(RTX 4070 Ti / Vulkan、キャンバス解像度)は 2048² で 0.34 → 1.76ms、1024² で 0.08 → 0.47ms。SimParams は 63 フィールド+パディング1 = 256B。**SimParams のレイアウトが変わったので再ビルド・再起動が必要**。要目視確認: status.md §1.6「色の縁のアンチエイリアス」。

**筆圧なしを常に 0 と読み、まとめて届いた点に筆圧を割り振る(2026-11-03、要目視確認)**: 前のエントリの修正を Fable(claude-fable-5-1)にレビューしてもらった。指摘は、筆入れの最初のイベントが `None`(軽い接触、ごく短い払い)だと 1.0 と読まれ、始点が丸く太くなりうること。あわせて、筆圧アルゴリズムの改善案(A まとめて届いた点の筆圧を補間 / B 速度による抜き / C 筆圧の平滑化)が出た。ユーザーは「`None` を常に 0」と案 A を選択。`PenSource` は `force: None` を常に 0 と読む(筆圧を返さない指タッチは最も細い線になるが、入力の対象は Windows Ink のペン)。ユーザーの記録 `test.json` では、1フレーム内の 3〜7 点が同じ筆圧になっていた。winit が1メッセージにまとまった過去の位置すべてに、受け取った時点の筆圧を付けるため。同じ筆圧で続けて届いた Move を1つのまとまりとし、直前のまとまりの筆圧から線形に割り振る `spread_bundles` を足した(パラメータなし。記録の前に掛けるので再生と一致する)。単体テスト `bundle_ramps_from_previous_pressure` / `steady_pressure_is_unchanged` を追加した。`test.json` には筆圧 1.0 の点も 0 の点もなく、払いの症状は入っていないので、根本原因の実機での裏付けは残っている。要目視確認: status.md §1.6「勢いよく払った末尾」。

**勢いよく払うと末尾が丸く太くなるのを修正(2026-11-03、要目視確認)**: ユーザー報告「筆圧関係で、勢いよく線を引くと最後のところが突然丸くなってしまうことがある」への対応。winit 0.30 の Windows 実装は、まとめて届いた過去の位置サンプルすべてに、受け取った時点の筆圧(`GetPointerPenInfo`)を付ける。また、筆圧 0 は `normalize_pointer_pressure` で `force: None` になる。勢いよく払うと、ペンが離れる直前の位置がまとめて筆圧 0 = `None` で届き、`PenSource` が `force.unwrap_or(1.0)` で最大の筆圧と読んでいたため、末尾に最大の太さの筆先が丸く現れていた。そのストロークで筆圧が一度でも届いていれば、`None` を 0 と読むようにした(一度も届かない指タッチ等は従来どおり 1.0)。e2e_ui `pen_lift_without_force_does_not_fatten_tail`(筆圧 0.15 の線の後に筆圧なしの Move を送り、末尾の脇が塗られない。修正前は落ちることを確認)を追加した。調べる過程で、`StrokeState::add_motion` が1区間の splat の間隔を終点の筆圧だけで決めていたことも見つけた。払いの最後の区間(遠くへ飛び、筆圧はほぼ 0)では、太い所に細い筆用の間隔で splat が何倍も詰まり、筆の中身を使い切って払いの先が薄く抜ける(幅は変わらない)。間隔を区間内の各地点の補間した筆圧から決めるようにし、`add_motion` は間隔の代わりに「筆圧 → 間隔」の関数を受け取る形にした(ライブ描画・記録の再生・ラスタ線画の履歴で共通)。e2e `fast_flick_tail_keeps_density`(払いの中心の濃さが胴の 6 割以上。修正前は 36%、修正後は 77%)を追加した。kittest は1フレームに積んだイベントを別々のパスで処理し、描かれないパスの splat が捨てられるので、e2e_ui の入力はイベントごとにフレームを進める。要目視確認: status.md §1.6「勢いよく払った末尾」。

**スポイトを「パレットの色を変える」から「筆に顔料を取る」へ(2026-11-03、要目視確認)**: ユーザー要望「スポイトをパレットの色を変えるのではなく、筆にだけ顔料をコピーする感じにしたい」への対応。案として、拾う対象(湿レイヤーの顔料だけ / 湿レイヤーがなければ表示色を4色混合で近似する併用 / 常に表示色を近似)、濃さ(標準の1回分に揃える / その点の濃さも写す)、旧スポイトの扱い(「色をつくる」へ移す / なくす)を出した。ユーザーは「湿レイヤーの顔料だけ」「標準の1回分」「色をつくるへ移す」を選んだ。ツールバーのスポイトと I キーは、クリックした所の湿レイヤーの浮遊+沈着(7×7 テクセルの平均、`GpuCanvas::read_wet_pigment`)の比で、洗った筆に合計1回分を取る(`BrushLoad::take_mix`)。割合 2% 未満の色は落とし、拾った中で一番多い色を `brush_channel` にする。顔料が 0.005/テクセル未満の所(紙・乾いた層だけの所)では何もせず案内を出す。I キーは水彩レイヤーでだけ効くようにした。表示色で選択中スロットを作る従来の動きは、「色をつくる」モーダルの色の横の 💧(閉じて拾い、開き直す)へ移した。design.md §4 の「スポイトの意味論」の行を更新した。要目視確認: status.md §1.6「スポイトで筆に取った色が拾った所と同じ色で塗れる」。

**e2e `wet_on_wet_blends_into_green_gradient` の段差の検査を色相から RGB の距離に(2026-11-03)**: 857a9f4(顔料の拡散 0.2 → 0.1 など)から、隣の行との色相の最大の段が 48°(閾値 45°)で落ちていた。段は y=244→248 の、彩度 0.07〜0.08 のほぼ灰色の行の間で出ていて、画像では黄 → 淡い緑 → 青がなめらかに移っていた。灰色に近い所では、色がわずかに揺れるだけで色相が大きく振れるので、指標が過敏だったと判断した。検査を「隣の行どうしの RGB の距離の最大 ÷ 上端(黄)と下端(青)の距離 < 0.35」に変えた。今の既定では 0.18。顔料の拡散・筆の勢い・にじみ拡張を 0 にして黄と青を1行で切り替わらせると 0.69 になり、くっきりした境目は検出できる。

**乾いた色の上に置いた色が境界なく馴染むように(2026-11-02、要目視確認)**: ユーザー要望「水は乾いた真っ白なところには広がってほしくないが、顔料がすでにあるところにはじわじわ広がってほしい」への対応。案(A にじみ拡張に沈着量の門 / B Curtis の毛細管層 / C 乾燥時に濡れの名残を残す)からユーザーが A を選択。velocity.wgsl のにじみ拡張(`wet_expand`)に、乾いたセルの沈着顔料(4ch の和)で 0 → 1 に上がる門 `mix(wick_bare, 1, smoothstep(0, wick_ref, 沈着量))` を掛けた(`wick_bare` 0、`wick_ref` 0.05 を追加)。最初は `wet_expand` 0.05 で実機を試してもらったところ「求めていたものと違う」。目的は「にじまなくした上で、色の上に色を置いたときに境界を出さずに馴染ませる」ことだった(焼き込んだ色は対象外でよい)。headless で乾いたシエナの帯を濡れた青の縦線で横切ると、0.05 では前線が約 10px で止まり、その内側で色が均されて前線に段ができていた(境界が外へ移っただけ)。前線の距離が足りないと見て、色のある所だけ顔料の拡散を水の毛細管と同じ重みにする門 `wick_mix` も試したが、段は残った。`wet_expand` を 0.05 / 0.2 / 0.5 × `wick_mix` 0 / 0.3 / 1 で乾燥後の帯の明度を比べると、0.2 で段が消え、青の中心から 30〜40px かけて元の茶へなだらかに戻った。`wick_mix` の差は見えなかったので削除した。`wet_expand` の既定を 0 → 0.2 にした。白い紙への広がりを見ていたプリセット `m1d-paper-streak-only.json` には `wick_bare: 1` を足した。e2e `color_blends_over_dried_paint_but_not_onto_bare_paper` を追加(帯に沿った明度の隣どうしの差の最大 < 0.025。にじみ拡張なしでは約 0.07。帯の遠くと白い紙は変わらない)。`wet_on_wet_blends_into_green_gradient` は色相の最大の段が 48°(閾値 45°)で落ちるが、`wet_expand` 0 でも同じ値で、この変更の前から落ちている。SimParams は 62 フィールド+パディング2 = 256B。**SimParams のレイアウトが変わったので再ビルド・再起動が必要**。要目視確認: status.md §1.6「乾いた色の上に置いた色が境界なく馴染む」。

**筆の流れで混ぜる: 筆の勢い・速度減衰・顔料の拡散の既定値を変更(2026-11-02、要目視確認)**: 渦の強化を採らなかった後、案C1(筆の流れを強く長く)を試した。headless で黄の溜まりを青の筆で X 字に速く横切る・two-color-adjacent を比べると、`brush_velocity` と `damping` だけを変えても舌状に押し流すだけでぼやけていた。`pigment_diffuse` も下げると、横切った筆の跡が帯で残り、交差が緑に、押しのけられた所が黄で抜けるなど筆の動きが形に出た(wet-on-wet の境目は狭くなる)。羽毛状の細部はどの組み合わせでも出なかった。候補(控えめ 1.0 / 0.02 / 0.1、はっきり 2.0 / 0.02 / 0.05)をユーザーが実機で塗り比べ、控えめを選択。既定値を `brush_velocity` 0.5 → 1.0、`damping` 0.05 → 0.02、`pigment_diffuse` 0.2 → 0.1 にした。e2e は閾値を変えずに全件パス。要目視確認: status.md §1.6「筆の流れで混ぜる」。

**移流に MacCormack 補正を足した。渦の強化は試して採らなかった(2026-11-02、要目視確認)**: 「混ざるときの情報量を増やす」の続きで、案C(流れで混ぜる)の選択肢(C1 筆の勢いを長持ち / C2 渦の強化 / C3 curl noise、共通の移流の補正)から、ユーザーが C2 + MacCormack を選択。advect.wgsl は MacCormack 補正を1パスで掛ける(戻り先を囲む4格子点でその場で前進移流、前進サンプルの4タップでリミッタ)。`advect_sharp`(既定 1、0 で従来のセミラグランジアン)。velocity.wgsl に vorticity confinement を足し `vorticity` で強さを決める。headless の比較(濡れた黄を青の筆で速く横切る / two-color-adjacent / 黄+青の平塗り、`advect_sharp` 0/1 × `vorticity` 数段階)で次のことが分かった。①MacCormack なしでは渦の強化はほぼ効かない。②1 セル間隔の渦度だと、濡れ領域の縁(乾いたセルの速度 0 が強いせん断に見える)で縁がほつれ、色が乾いた側へ散って淡くなった → 2 セル間隔にして、縁から 4 セル以内では掛けないようにした。③上限なしの力は `vorticity` 1 では何も起きず、2 で減衰を上回って一気に乱流になった。色が細かくざらついて淡く見え(顔料が粒に集まると平均の被覆が下がる)、wet-on-wet の緑のグラデーションが黄と青に分かれた → 足す速さを「減衰で失う分 × `vorticity`(0〜1)」に抑えて必ず安定にしたが、今度は見た目の差が出なかった。④筆の勢い 2・減衰 0.02 にすると、横切った筆が色を押しのけた形は見えるが、渦の強化を足しても変わらない。混ざりの形を決めているのは流れの強さと顔料の拡散で、移流のぼけや渦の不足ではない。効かない機構は残さないというユーザーの判断で、渦の強化(`vorticity`)は削除した。MacCormack は見た目の差はほぼないが、流れを強めたときに筋を保つのと、コストが小さいので既定 on にした。perf(2048² 全面計算): 4.45 → 4.55 ms(MacCormack)、`vorticity` on で 4.57 ms。SimParams は 60 フィールド = 240B(パディングなし)。**SimParams のレイアウトが変わったので再ビルド・再起動が必要**。要目視確認: status.md §1.6「移流の MacCormack 補正」。

**混ぜた色に色むらを残す: 顔料の溜まりやすさによる寄り(2026-11-02、要目視確認)**: ユーザー要望「絵の具が混ざっていく時にある程度の色むらができ、情報量が増えるようにしたい」への対応。混ざりが diffuse.wgsl の等方的な拡散だけで、係数がどこでも同じなので、なめらかなグラデーションにしかならなかった。案(A 拡散を場所で不均一に / B 筆の中で混ざりきらせない / C 流れで混ぜる / D 乾き際の不均一)からユーザーが A を選択し、A の中の2方式(拡散のしやすさを紙目で変える / 顔料を紙の谷へ寄せるドリフト)から後者を選択した。拡散の流束に顔料ごとのポテンシャル φ の差で偏る項を足し、濡れている間は c ∝ exp(−φ) へ向かうようにした(対称な流束で総量は保存、偏りは安定条件から ±0.25 に制限)。φ = `paper_drift` × γ × 紙ハイトだけだと、紙ハイトの 2〜6px の成分に反応して粒状感のざらつきになり、γ の低い黄・青には効かなかった(headless の計測で、シェンナ+フタロの明度の標準偏差は寄り 0 / 2 / 4 / 8 で 0.006 / 0.012 / 0.022 / 0.040、黄+青ではほぼ不変)。ユーザーの選択で、全顔料に効く数十 px 規模の `mix_mottle` を足して2つの規模に分けた。紙テクスチャを r32float → rgba32float にし、g, b に斑の場を2枚置き、顔料スロットごとに 0°/90°/45°/135° の向きで組み合わせる(同じ場だと濃淡だけが揃って揺れ、色が揺れない)。斑の場を値ノイズで作ると、効きを上げたときに格子の四角が浮き出たため、オクターブごとに座標を回したグラディエントノイズにした。効きは指数的で、4 では黄と青が分かれて白い隙間ができたので、スライダーは 0〜4。既定は実機で見たユーザーの判断で、控えめな `paper_drift` 1・`mix_mottle` 0.3(1 / 3 では強すぎた)。これで既知の課題「γ が見た目に効かない」も片付いた。SimParams は 59 フィールド+パディング1 = 240B。e2e_ui `pen_pressure_changes_stroke` は、線の中心1点の濃さを比べていた。筆圧で濃さを変えない仕様では、強い線と弱い線の差はもともと2割ほどで、混ざりムラの揺れで逆転したので、太さ(中心から外した位置)だけを見るようにした。**SimParams のレイアウトと紙テクスチャの形式が変わったので再ビルド・再起動が必要**。要目視確認: status.md §1.6「混ぜた色の色むら」。

**e2e を実 GPU で回すように(2026-11-02)**: ユーザー要望「テストの実行を速くしたい」への対応。計測すると差分ビルドは約 6 秒で、`cargo test --workspace` の 451 秒のほぼすべてが e2e の実行(e2e_watercolor 327 秒 / e2e_ui 88 秒 / e2e_video 32 秒)だった。egui_kittest の `default_wgpu_setup` は CPU アダプタを優先するため、Windows では DX12 WARP(Microsoft Basic Render Driver)で流体シミュレーションを回していた。`tests/common::render_state` でディスクリート → 内蔵 GPU の順に選ぶようにし、RTX 4070 Ti(Vulkan)で全件パスのまま 15 秒(e2e_watercolor 5.0 秒 / e2e_ui 2.7 秒 / e2e_video 1.3 秒、ビルド込み)になった。`KASANEIRO_TEST_ADAPTER=cpu` で従来の WARP に戻せる。perf_bench も同じ関数を通るので、Windows でこれより前に測った値は WARP のもの。

**`paper_gran` を上げても粒状感が出ないことの計測(2026-11-02)**: 既知の課題「γ がほぼ効かない」に対し、既定値を上げる案をまず試した。幅 60px の帯をバーントシェンナ(γ 0.8)・フタロブルー(γ 0.05)・ハンザイエロー(γ 0.1)で塗って乾かし、帯の内側の明度の標準偏差を比べると、シェンナで `paper_gran` 0 / 1 / 2 = 0.0045 / 0.0048 / 0.0056 となり、目で見ても差は分からなかった。transfer.wgsl の `paper_gran` は沈着の速さを変えるだけで、浮遊顔料は乾くまでにすべて沈着し、乾きかけでは拡散がほぼ止まって紙の谷へ顔料が移らないので、最終的な沈着量の分布は変わらない。既定値は 0 のまま。

**色スウォッチの押下を持ち替えに(2026-11-02)**: status.md の既知の課題「色を持ち替えるには洗ってから取る」への対応。案(Shift+押下を持ち替えに / 押下を持ち替え・Shift+押下を足すに)から、ユーザーが後者を選択。押した瞬間に筆を洗ってからその色を1回分取り、Shift を押しながらだと従来どおり今の筆の色に足す(押し続けている間に取り続けるのはどちらも同じ)。ダブルクリックで「色をつくる」を開いたときは、従来どおり1回目より前の中身へ戻す。e2e_ui に `swatch_switches_color_and_shift_mixes`(黄 → 青と押した線は青、Shift+黄を足した線は緑寄り)を追加。

**筆圧が弱いときにかなり細く塗れるように(2026-11-02、要目視確認)**: ユーザー要望「細かいところまで塗りたいので、筆圧が小さい時にはかなり小さく塗れるように」「筆圧による濃さの変化はほぼ要らない」への対応。既定の筆圧の効きを半径 0.6 → 1.0(完全比例。筆圧 0 で実効半径の下限 0.5px まで細くなる。以前は基準半径の 40% 止まり)、顔料量 0.7 → 0、水量 0.3 → 0 にした。水量も筆圧で減らすと紙が濡れきらず細い線が薄くなるため。さらに、細い線だけ薄くなる原因が splat の間隔の下限 1px だった(半径 1.6px の線では1セルをなぞる回数が太い線の約 1/3 になり、紙が穂先の濡れ具合まで濡れきらない)ので、下限を 0.25px にして式を `SimParams::splat_spacing` にまとめた(ライブ描画・記録の再生・ラスタ線画の履歴が共有)。半径 16 で筆圧 1.0 / 0.3 / 0.1 の線の幅は 32 / 10 / 4px、筆圧 0.1 の線の中心の濃さは筆圧 1.0 の 47% → 80%。e2e に `light_pressure_paints_thin_lines`(幅が筆圧で単調に細り、筆圧 0.1 で 1/4 以下、中心の濃さは 7 割以上)を追加。`washed_brush_trail_has_no_beads` は線が細くなって、始点と終点を結ぶ直線で明度を取ると曲がった軌跡の縁の段差を拾っていた(軌跡は直線から最大 7.8px ずれる)ので、記録した軌跡に沿って取るようにした(RMS 0.0011)。要目視確認: status.md §1.6「筆圧で細く塗る」。

**洗った筆でなぞった跡が段々になるのを修正: 筆の勢いを出た水の運動量に(2026-11-02、要目視確認)**: ユーザー報告「乾いた筆でなぞると段々になる。吸ってすぐ描くのを繰り返しているせいか」(濃く塗った上を「洗う」をした筆でなぞると起きる)。ユーザーの記録 `test` をヘッドレスで再生して再現し(`assets/strokes/washed-brush-over-dense.json` として同梱)、穂先の中身を1フレームずつ追うと、溜まりでは吸う一方・出た先でゆっくり出すだけで、吸う/出すの繰り返しは起きていなかった。フレーム内の予測 `Splat.scale`・置いたままの splat・溶かし戻しを1つずつ切っても変わらず、`brush_velocity` を 0 にすると消えた。原因は splat.wgsl が空でない筆の動く splat ごとに `vel += coverage × brush_velocity × 進行方向` を足し込んでいたこと: 洗った筆も吸い始めた次のフレームから紙の水を満タンの筆と同じ強さで押し、薄い水が浮遊顔料ごとフレームごとの濡れた所の前縁へ寄って輪が残る(輪の間隔は記録の入力の来方 = 1フレームに splat 2個・4個の交互の2フレーム分)。改善案3つ(出た水の運動量 / 穂先の濡れ具合を掛ける / 足し込みをやめて寄せる)からユーザーが案1を選択。穂先から出た水 `f` と紙の水を運動量で混ぜる形にした(`vel = (vel × water + v × f) ÷ (water + f)`)。運動量だけでは乾いた紙(紙の水 0)で出た水がそのまま筆の速さを持ち、縞の揺れが4割ほどに減るだけだったので、出る水の速さに穂先の濡れ具合を掛けた(満タンの筆はほぼ以前の勢い)。e2e: `washed_brush_trail_has_no_beads`(最後の1本の、溜まりを出た先の筋の明度の、15px 移動平均からの揺れ RMS < 0.0025。修正前は 0.0036 で落ちることを確認)を追加。`paint_brush_picks_up_wet_color` は、筆が溜まりの水を押し寄せて吸っていた分がなくなり、通った後の穂先の水が 0.093(溜まりなし 0.033)になったので、下限を 0.15 → 0.07 に(黄の濃さ 1.12、先へ運ぶ検査は通る)。要目視確認: status.md §1.6「筆の勢いを出た水の運動量に」。

**洗った空の筆で絵の具を吸い取れるように(2026-11-01、要目視確認)**: ユーザー要望「『洗う』で筆をリセットした後にキャンバスの絵の具を吸いたい」への対応。空の筆(水 0)は splat.wgsl で何もしなかったが、乾いた穂先として受け渡しの式を通すようにした(紙の濡れ具合 > 0 なら f < 0 で吸うだけ。紙へは出さず、乾いた紙を濡らさず、初速も溶かし戻しも与えない)。置いたまま動かない splat も筆の残量で止めず常に積むので、空の筆を濡れた所に置いたままでも吸う。穂先が満ちると吸わなくなり、吸った色を置く筆になる。e2e `washed_brush_lifts_wet_paint`(乾いた紙では何も付かず筆も空のまま、濡れた黄の中では穂先が黄を吸って跡が淡くなる)を追加。あわせて、筆の大きさ 500px で e2e の wet-on-wet の緑の彩度が 0.06〜0.08 になったので下限を 0.08 → 0.05 に(画像で黄 → 緑 → 青のなめらかな移りを確認。全体が淡いのは受け入れ済み)、減り方の検査は「戻りの減りが行きの半分以下」の比にした。要目視確認: status.md §1.6。

**塗る筆を「穂先と腹」の2室にし、紙と濡れ具合の差で受け渡す1本の式にした(2026-11-01、要目視確認)**: 前のエントリの吸い込みでは「置く(筆跡ごとに足す)・減る(なぞった距離)・吸う(水位の差)」が別々の単位で動いていて、吸った量の換算に正解がなかった(ユーザー報告「乾きかけの筆で吸うのがあまり起きない」)。ユーザーの「アルゴリズムをちゃんと考えたい」を受けて [memo/2026-11-01-brush-exchange.md](memo/2026-11-01-brush-exchange.md) で整理し、①筆と紙が濡れ具合の差で水を受け渡す1本の式(量は保存。顔料は出るとき筆の濃さ、入るとき紙の浮遊顔料の濃さ)②フレーム内は CPU が乾いた紙での減りの上限を splat ごとに予測(案 e)③紙が満タンの水位 = `brush_water` × 4.3(1回なぞって均された後の水位の計測値)を選んでもらった。実装すると、量は釣り合うが1室だと吸える量が溜まりの水で頭打ちになり、乾きかけの筆が吸った色を運べなかった(比較は artifact で共有)。そこで [memo/2026-11-01-brush-tip-belly.md](memo/2026-11-01-brush-tip-belly.md) の案 A「穂先(紙と受け渡す、小さい)と腹(穂先へ送る、大きい)の2室」を選んでもらい、補充は腹 → 穂先の一方向、筆を上げている間の補充は次に塗るフレームでまとめて、時間はシミュの刻みで数える。**変更**: splat.wgsl の描画分岐は穂先と紙の受け渡しの式1本(feed splat の `max` 補充・`CHARGE_PIGMENT` と吸い込みの換算を撤去)。集計は `atomic<i32>`(符号付き)。brush.wgsl は集計を穂先へ反映して腹から補充。筆バッファ 32B → 64B。`SplatHeader` の空きを `brush_dt` に。`BrushLoad` に `tip: Option<Chamber>`(None = 腹と同じ。古い記録・保存はこれで読める)、スウォッチ操作は両方の室にかける。`BrushFrame` は距離の減りと feed の時間をやめ、穂先の残りの予測 `scale` と補充の時間 `dt`、`BrushClock` が刻みを溜める。SimParams: `brush_charge`・`brush_absorb` を削除、`brush_exchange`(0.3)・`brush_tip`(80px)・`brush_refill_time`(0.05 秒)を追加、`brush_hold` は腹の大きさ、`brush_water` は紙を濡らす水位の意味に。57 フィールド+パディング3 = 240B。`FOOTPRINT_RATIO` / `CROSS_RATIO` / `SAT_RATIO` を sim.rs に置いてプレリュードで共有。UI: 塗る筆に「筆の大きさ」「穂先の大きさ」、開発モードに「受け渡しの速さ」「腹から穂先へ送る時間」、筆の状態パネルは穂先と腹それぞれの水と顔料のゲージ(色見本と内訳は穂先の色)。**自動補充の既定を off に**(ユーザーの指定)。既定値は e2e で、穂先 150px・補充 0.3 秒では普通の速さ(約 320px/秒)で穂先が 74% まで下がって線が淡くなったので、穂先 80px・補充 0.05 秒(穂先が約 88% を保つ)にした。筆の大きさ(`brush_hold`)の既定は、実機で「筆の水が全然減らない」と感じたため 2000px → 500px に下げた(計測: 2000px では乾いた紙にキャンバス幅の線を5本引いて腹 0.65、同じ線の往復では 2400px でも 0.87。濡れた所で減らないのは紙が水を吸い込む仕組みが無いためで、design.md §4 に先送り)。**全体の色は以前より薄い**(筆跡の重なりで顔料が積み上がらなくなったため。ユーザーの判断で、いったん薄いまま)。e2e: `full_brush_depletes_on_dry_paper_only`(乾いた紙で減り、普通の速さで穂先が乾かず、戻りでほとんど変わらない)と `paint_brush_picks_up_wet_color`(水 5% の透明な筆が黄の溜まりを通ると穂先が濃さ約 0.98 の黄になり、先の紙へ運ぶ)。**SimParams・Splat・筆バッファのレイアウト変更なので再ビルド・再起動が必要**。要目視確認: status.md §1.6「塗る筆の受け渡し・穂先と腹」。

**塗る筆が自分の水を吸い戻して減らなかったのを修正(2026-11-01)**: ユーザー報告「筆の水や顔料が減らない。描いたらすぐに吸ってしまってるかも」への対応。原因は2つ。①吸うかどうかを筆跡1つの水位と比べていたが、1回なぞると各セルに筆跡が約 6.4 回重なって置かれるので、置いたばかりの自分の水を常に吸い戻していた。②吸った量を筆跡1つの量で割って筆の単位に直していたので、筆が実際に減る量(なぞった長さ。含みの持ち 2000px で半分)に比べて数百倍に数えていた。筆の水位を「1回なぞったときの水位」(`stroke_overlap()`)にし、吸った量は「満タンの筆が一生で置く量」(× `brush_hold` ÷ ln2 ÷ 間隔)を 1 として足すようにした(置いた分以上は戻らない)。`brush_hold`=0 の減らない筆は吸わない。splat の間隔 0.25 を `paint_core::sim::SPLAT_SPACING` にしてプレリュード経由で WGSL と共有した。e2e に `full_brush_still_depletes_over_own_stroke`(往復しても見込みどおり減る。修正前の式では水 1.0 のままで落ちることを確認)を足し、`paint_brush_picks_up_wet_color` は水 5% の乾きかけの筆で筆の濃さを見る形にした。要目視確認: status.md §1.6「塗る筆の吸い込み」。

**塗る筆が紙から色を吸う(2026-11-01、要目視確認)**: ユーザー要望「筆で絵の具を吸い取る挙動を実装したい」への対応。design.md §4 の先送り「紙から色を吸う」の再検討トリガー(筆の汚れ・色の持ち運び)にあたる。削り・吸い取りは今のまま、塗る筆だけが吸う。案から「紙と筆の水位の差で吸う」と「筆の中身を GPU へ移してフレーム単位で更新」を選んでもらった。筆の中身を GPU の筆バッファ(`GpuBrush`、binding 12)に移し、splat.wgsl の描画分岐で紙の水位が筆の水位を超えたセルから水と浮遊顔料を吸って atomic の集計(binding 13)へ足し、新しい brush.wgsl がなぞった減り・置いたままの含み・吸い込みを中身へ反映する。CPU は `BrushFrame`(置き換え・なぞった減り・含みの時間)を渡し、中身は非同期で読み戻して表示する。`Splat` は筆の中身を運ばなくなり 48B → 32B(`water` / `pigment` → 置く時点の残りの割合 `scale`)、ヘッダのパディングを `brush_scale` / `feed_dt` にした。`BrushLoad::load_splats` / `feed` は `BrushFrame::drag` / `feed` に置き換え、`Player::advance` は `BrushFrame` も受け取る。SimParams は末尾パディングを `brush_absorb`(既定 0.3、塗る筆の設定に「筆が色を吸う」スライダー)にして 224B のまま。実装中、置き換えをフレームのコールバックに載せると egui が組み直して捨てたパスの分が届かず「洗う」が効かないことがあったので、アプリからの置き換えはその場で write_buffer する形にした。e2e に `paint_brush_picks_up_wet_color` を足し、前のコミットで説明文が変わって落ちていた e2e_ui `tool_button_switches_tool` の文言を直した。**SimParams と Splat のレイアウト変更なので再ビルド・再起動が必要**。要目視確認: status.md §1.6「塗る筆の吸い込み」。

**削りを濡らして吸い取る形に(2026-11-01、要目視確認)**: 「削りと水だけの筆の違い」を整理した結果、どちらも沈着顔料を浮遊層へ戻すだけで、差が係数(0.3 / 0.2)と紙目ゲートくらいしかなかった。ユーザーの選択で、削りを実際のリフトと同じ「濡らして浮かせ、押さえて吸う」形にした。splat.wgsl のリフト分岐で、浮かせた後に吸い取りと同じ式で水・浮遊顔料・速度を `lift_blot`(新規、既定 0.5)の割合で取り去る。SimParams は末尾パディングの1枠を使って 224B のまま。削りのツール設定に「押さえて吸う」スライダーを追加。**SimParams のレイアウト変更なので再ビルド・再起動が必要**。要目視確認: status.md §1.6「削り = 濡らして吸い取る」。

**洗うで空の筆に(2026-11-01、要目視確認)**: ユーザー要望「洗うはリセットとして水の量も 0 にしたい。その後に水を押せば水だけになる」への対応。`BrushLoad::wash` を水も顔料も 0 の `empty()` にし、水だけの筆は `water_only()`(旧 `clean()`)として残した。起動時・記録再生の初期の筆も空。空の筆(`Splat.water` が 0)は splat.wgsl の描画ブランチで何もしない(水 0 でも濡れマスクを立てて下の色を溶かしていたため)。e2e_ui の濃さの描き分けは「洗う → 水」の線で確かめる形にし、load に「洗うと空・水で水だけ」の1件を足した。要目視確認: status.md §1.6「ぼかし筆の統合・洗うで空の筆」。

**ぼかし筆を塗る筆へ統合(2026-11-01、要目視確認)**: ユーザー要望「筆の水と顔料を入れたことでぼかし筆などと機能が被ってきたので整理したい」への対応。重なり(ぼかし筆 ≒ 洗った筆で塗る、吸い取り ≒ 水の少ない筆、「顔料量」スライダー ≒ 色を取る長さ)を挙げ、案(ぼかし筆だけ廃止 / ぼかし筆と吸い取りを筆の水分で連続化 / UI だけ整理)から、ぼかし筆だけ廃止を選んでもらった。`WetTool::WaterBrush` と splat.wgsl の分岐、`SimParams::water_lift` を削除し、吸い取りの tool 値を 4 → 3 に詰めた(tool=3 の旧ぼかし筆で記録したストロークは吸い取りとして再生される)。ぼかしの強さは塗る筆の「下の色を溶かす」(`paint_pickup` 0.2。旧 `water_lift` は 0.3)が兼ねる。違いとして、洗った筆は水を目標水位まで上げる(`max`)のではなく足すので、なで続けると水が増える。「顔料量」(`brush_pigment`)スライダーは開発モードの「筆」へ移した。SimParams は `_pad_brush: [f32; 2]` で 224B のまま(プリセットに残った `water_lift` は無視される)。**SimParams のレイアウト変更なので再ビルド・再起動が必要**。要目視確認: status.md §1.6「ぼかし筆の統合」。

**筆の中身(2026-11-01、要目視確認)**: ユーザー要望「筆に含まれる顔料の概念を扱いたい」への対応。アイデア整理で、体験の軸(減る/拾って運ぶ/濃さの描き分け/2色の含ませ)と実装案(在庫だけ/双方向/段階導入)を出し、**濃さの描き分けを先に作り、色を吸う機能は後から足せる形にする**ことと、補充は自動と手動の両方を持つことを決めてもらった。取る操作の形は「キー+表示/水入れと絵具皿/スライダー併用」の3案のうち、ユーザーの指摘で「水のスウォッチを足して色と同じ操作で取る」にまとめ、完全に洗う手段として「洗う」の領域を足した。**仕組み**: [crates/paint-core/src/load.rs](../crates/paint-core/src/load.rs) に `BrushLoad`(水 1 = 満タン、4スロットの顔料 1 = 標準の1回分)を追加。`Splat` を 32B → 48B にして `water` と `pigment: vec4` を運ばせ、[splat.wgsl](../assets/shaders/splat.wgsl) の描画ブランチは `brush_water`×`s.water` / `brush_pigment`×`s.pigment` を4スロットへ同時に注ぐ形にした。なぞると `brush_hold`(既定 2000px で半分)に従って水と顔料が同じ割合で減る。置いたままの色水(feed)は時間の含み(`charge_left`)をやめ、筆の中身の水を使う(満タンで `brush_charge` 秒)。ツールバーは色4つ+水+洗う: 色は押した瞬間に1回分+押している間 1/秒、水は押した瞬間に顔料半分+時定数 0.25 秒で抜け、合計 0.02 未満で 0 に切る。自動補充(既定 on)は筆を下ろすたびに最後に作った中身へ戻す。筆の中身(戻り先)と自動補充は eframe storage に保存し、初回は洗った筆で始める。ストローク記録は `RecordedStroke.load` に筆を下ろした時点の中身を残し、`load` の無い記録はその顔料スロットの標準1回分で再生する。**分離色の `brush_channel2` / `brush_mix` は削除**(2色を筆に取れば同じことになる)。SimParams の枠は `brush_hold` と末尾の `_pad_brush` へ(224B 不変、プリセットに残った旧フィールドは無視される)。**SimParams と Splat のレイアウト変更なので、実行中アプリへの WGSL ホットリロードだけでは整合しない — 再ビルド・再起動が必要**。テスト: paint-core に load の8件と記録再生・Splat レイアウトの各1件、pigment に混色表示の1件、e2e_ui に「青 > 水で薄めた青 > 洗った筆」の濃さの描き分け1件を足した(既存の e2e_ui は描く前に色を取るよう直した)。全84件・clippy 警告0。**要目視確認**: status.md §1.6「筆の中身」の項。

**乾いた層の濃さ(2026-11-01、要目視確認)**: ユーザー要望「固定した色の濃度を調整したいかも」への対応。方式は案(層ごとの濃度倍率 / 層の不透明度 / 顔料テクスチャへ焼き込み)から、戻せて水彩らしく薄まる濃度倍率を選んでもらった。`DriedLayer` に `density`(既定 1)を足し、`LayerUniform` に重ね順の倍率配列を足して `dried_cache_main` が読んだ顔料濃度に掛ける。乾いた層を選んだときの左パネルに「濃さ」スライダー(0〜2)と「1 に戻す」。下地への統合ではその倍率のまま焼き固める。作品ファイルのレイヤー構成に `density`(省略時 1、負・非有限は拒否)を足した(識別子は KSN1 のまま)。e2e `dried_layer_density_scales_look` で、倍率の順に濃さが並び、0 で紙に戻り、1 に戻すと元の絵と一致することを確かめた。テストは全72件。要目視確認は status.md §1.6

**リプレイの動画書き出し(2026-11-01、要目視確認)**: ユーザー要望「replay を動画にする機能が欲しい」への対応。方式は案(ffmpeg に流す / PNG 連番 / GIF 自前)と入口(再生パネル / CLI / 両方)から、ffmpeg + 再生パネルを選んでもらった。[src/video.rs](../src/video.rs) を追加し、保存済みストロークの行に「🎬 動画」ボタンを足した。別スレッドで画面と同じ Device / Queue から `HeadlessCanvas` を作り、記録を `Player` で再生しながら毎フレーム `snapshot` を ffmpeg(rawvideo RGBA → libx264 / yuv420p / crf 18、60fps)の stdin へ流す。再生後 2 秒の余韻まで撮る。キャンバスサイズ・パラメータは書き出し開始時の値、パレットは記録時のもの。進捗バーと取り消し(書きかけは消す)あり。ffmpeg は `KASANEIRO_FFMPEG` → exe 隣 → PATH の順に探し、Windows では `CREATE_NO_WINDOW` で起動する。出力は `videos/`(git 管理外)。依存クレート・SimParams・シェーダーは不変。テスト [tests/e2e_video.rs](../tests/e2e_video.rs)(書き出し・取り消し。ffmpeg が無ければ飛ばす)。macOS で 512² の書き出しを確認(121 フレーム、途中と最後のフレームを目視)。要目視確認: Windows での ffmpeg の見つけ方とコンソール非表示、2048² 書き出し中の画面の引っかかり、動画と画面再生の見た目の一致。

**固定刻み・乾いたタイルの停止・下地への統合(2026-11-01)**: 設計レビュー(要件に対して今の設計は妥当か)で挙がった懸念の上位3件への対応。ユーザーの「1,2,3やりますか」で、それぞれ推奨案(固定刻み+積み立て / 判定だけ変える / 下地に焼き固める)を選んでもらってから実装した。**①時間**: シミュのステップがフレーム数で決まっていたため、144Hz では 60Hz の約2.4倍速く乾き、e2e(1/60 秒)や別機種での記録再生ともずれていた。[crates/paint-core/src/clock.rs](../crates/paint-core/src/clock.rs) の `SimClock` が経過時間を 1/60 秒の刻みに積み立て(1フレーム最大4刻み)、`sim_steps = 刻み数 × 速度倍率` にした。ストローク記録・再生も刻み単位(JSON のキーは `frame` のまま。60Hz で録った既存の記録はそのまま同じテンポ)。**②乾いたタイル**: 濡れマスクは蒸発では消えないので、一度濡れたタイルは Fast Dry・乾かすまで計算され続け、長く描くと全面計算へ近づいていた。tilescan の判定を「濡れマスクが立ち、水・速度・浮遊顔料のどれかが残る」に変えた(シミュの式は変えていない。水・速度・浮遊が 0 のセルは全パスで不動点。浮遊は沈着で指数的に減るので 1e-6 以下は止める)。2048² で全面を濡らして蒸発させた後のフレームが 18.1ms → 2.8ms(main の tilescan に差し替えた同条件の計測と比較)。e2e `active_tiles_match_full_compute_after_evaporation` で、水が尽きた跡の隣に水を置いても全面計算と同じ絵になることを確かめた。**③乾燥レイヤーの8枚上限**: 上限に達すると「リセットしてください」しか手がなかった。`GpuCanvas::merge_into_base` が下から N 枚を乗算・KM の両方式で合成キャッシュに焼いて下地(rgba16float 2スライス)へ写し、残りの層をスロット 0.. へ詰め直す。合成は下地(なければ紙)から始まる(`LayerUniform` の `has_base` / `force_mode`)。レイヤーパネルの各乾いた層に ⤓(その層から下を統合)を足した。作品ファイルはメタに `has_base`(省略時 false)、下地があれば末尾に f16 のブロブを足す(識別子は KSN1 のまま、下地のない作品は従来の並び)。e2e `merge_into_base_keeps_look` で、交差する3層の下2層を統合しても両方式で最大差 2/255 以内、統合後にまた乾かせることを確かめた。perf_bench に「全面濡れの蒸発後」の列を足した。テストは全69件。**要目視確認**: 144Hz など 60Hz 以外での乾く速さ・記録再生のテンポ、診断モード7で水が尽きた数秒後にタイルが暗く戻ること、⤓ の統合で見た目が変わらないこと・統合した作品の保存と読込(status.md §1.6)

**水の毛細管拡散でアルゴリズムを一次原理化(2026-07-09、目視調整4ラウンドを経て main へマージ=採用済み)**: 「そもそものアルゴリズムは無駄に複雑になってないか」「パラメータが増えると今後の拡張が難しくなる」というユーザー指摘への対応。置き馴染み(水のテレポート)と広がる勢い(relax と綱引きする放射流)は、どちらも**毛細管現象(水自身が濡れた紙を伝って広がる力)がモデルにない**ことへの現象論パッチだったので、[diffuse.wgsl](../assets/shaders/diffuse.wgsl) に**水量そのものの拡散**(簡易 Richards、流束の重み = max(両セル水量)^γ、質量保存・マスク境界 Neumann・ペン線透水率/アクティブタイル対応)を追加して両方を廃止した(設計判断・A/B の観点は [note/07](memo/2026-07-09-capillary-water.md))。あわせて transfer の吸着を (2−w)×(1−0.7w) の2重カーブから `deposit_weight(w)` の1本に統合(当初は旧同値の単調減少 → 目視「沈着が速すぎる」を受けて**しきい値型** `mix(2.0, DEPOSIT_WET_FLOOR, smoothstep(0, 0.35, w))`=水膜が切れるまで沈まない、へ変更。目視2回目で床 0.3→0.1)。目視3回目「既存色が新しい塗りへ戻らない」で `lift_rate` 既定 0.02→0.1(既存色の復路は再浮遊→拡散だけのため。note/07)。目視4回目「乾き際の紙のざらざら感」で velocity.wgsl に `FLOW_MIN`=0.3(薄い水膜の流れ止め=潤滑近似。しきい値型吸着で低水量まで浮遊するようになった顔料が、紙目駆動の流れで谷へ寄るのを防ぐ)。続けてユーザー判断「**紙の質感再現は要らない**」により `paper_amp`/`paper_gran`/`paper_wet` の既定を全て 0 に(機構・紙ハイトテクスチャ・スライダーは残置=戻すのは値を上げるだけ。副作用: 顔料個性 γ(粒状感)は paper_gran=0 だとほぼ不活性。鉛筆の粒状感 pencil_gran は対象外)。しばらく使って確定なら、紙ハイト機構ごと削る掃除は別途(R 項目相当)。`paint_spread` は削除(広がる距離は brush_water×brush_charge という物理から出る)し、塗るツールのノブは**筆の含み・下の色を溶かす**の2本に。feed splat は目標水位への max 補充+CHARGE_PIGMENT の顔料のみ。新定数: `WATER_DIFFUSE`=0.15 / `WATER_GAMMA`=2.0(diffuse.wgsl)・`DEPOSIT_WET_FLOOR`=0.1 / `DEPOSIT_DRY_POINT`=0.35(transfer.wgsl)。`SOAK_RADIUS`・`WET_HOLD` は消滅。SimParams 224B 不変(`_pad_paint: [f32;2]`)。検証(cargo test --workspace 全32件 / clippy --workspace 警告0 / naga=別 target dir)+実機の目視調整4ラウンド(上記)。採否の判断は plan.md §4 の先送り表(流体ソルバ・紙の質感の行)に記録。残る目視観点(含みでの保持広がり・白紙輪郭の不変・「押しのける」表情の要否)は通常使用の中で確認し、距離が足りなければ WATER_DIFFUSE/WATER_GAMMA をホットリロードで増強、表情不足なら弱い放射流のハイブリッド(note/07 §5)。

**KM の設計判断**: 層「内」の混色は M1c の mixbox のまま(RGB 3ch の K,S で混ぜると黄+青が濁り、mixbox に移した意味が消える)。**KM は層「間」の光学スタックだけに使う**。各層の反射率 R・透過率 T は、その層を白地・黒地に置いた mixbox 発色 R_w, R_b から導く(単層を白/黒地に置いた合成式を逆に解くと `R=R_b`, `T²=(R_w−R_b)(1−R_b)` と閉じた形になり sinh/cosh 不要 = オーバーフロー対策も不要)。この簡約が Curtis 一般式と一致することを km.rs のテスト(reduction_matches_general)で担保。**「顔料ごとの K,S プリセット」は不採用**とし、代わりに白/黒地発色から層単位で導出する方式にした(mixbox 隔離 = plan §4 を保ち、混色モデルを二重化しないため)。GPU 配管は黒 latent を pigment.rs の latent_uniform に追加([12],[13])しただけ。パラメータ追加: `compose_mode`(既定 1=KM。SimParams 末尾で 16B 境界を担う)。
