# かさねいろ(kasaneiro)設計方針と先送り判断

開発の進め方の原則(§1・§2)と、いま決めないことの一覧(§3)。各マイルストーン・装備の実装状況は [status.md](status.md)、技術調査は [note/00-overview.md](note/00-overview.md) 起点のノートを参照。

**設計方針: 試行錯誤の速度を最優先する。** このプロジェクトの品質はアルゴリズムの選択ではなく**パラメータ調整の反復回数**で決まる([01](note/01-fluid-simulation.md) §1「パラメータ調整が見た目を大きく左右する」、[05](note/05-rust-feasibility.md) §7「調整作業の大半=シェーダーパラメータいじり」)。そこで次の2点を構造として組み込む:

1. **シミュレーション本体より先に調整ループを回す道具を持つ** — ホットリロード・パラメータパネル・デバッグ表示・ストローク再生(装備 H1〜H6)
2. **完了条件は「目で見て判定できる体験」で定義する** — 数値目標ではなく「2色が馴染んで綺麗なグラデーションになるか」のような体感チェックにする。判定できないものは作りすぎのサイン。e2e テストもこの方針で、数値を固定せず体験が壊れていないかだけを見る

---

## 1. 試行錯誤ループの設計(このプロジェクトの心臓部)

理想の調整ループは以下で、**1周を数秒以内**に収める:

```
パラメータを1つ動かす(スライダー or WGSL編集)
  → 同じストロークが自動で再描画される(ストローク再生)
  → 前の結果と見比べる(スナップショット比較)
  → 良ければプリセット保存、悪ければ戻す
※ どこにも再コンパイル・再起動・手描きのやり直しが入らない
```

これを支える6つの装備(実装場所は [status.md](status.md) §3):

| # | 装備 | 内容 | 効果 |
|---|---|---|---|
| H1 | **WGSLホットリロード** | シェーダーをファイルから実行時ロード。ファイル監視(notify クレート)で保存即再コンパイル。コンパイルエラーは画面にオーバーレイ表示し、直前の正常なパイプラインで続行(クラッシュさせない) | シェーダー編集で Rust 再コンパイル不要に。**調整作業の大半をカバー** |
| H2 | **パラメータパネル** | 全シミュレーションパラメータを単一の `SimParams` 構造体に集約し、そのまま uniform buffer として GPU へ。egui スライダーは構造体のフィールドと1対1。**パラメータ追加 = フィールド1行+スライダー1行+WGSL1行**の定型作業にする | スライダーはリアルタイム反映。蒸発率・沈着率などをその場で動かせる |
| H3 | **プリセット保存/読込** | `SimParams` を serde で JSON 化して `assets/presets/` に保存・読込。**プリセットは git にコミットする**(「昨日の良かった設定」を失わないため) | 試行錯誤の成果が蓄積される。悪化したら即戻せる |
| H4 | **デバッグ表示切替** | 表示モードを切り替えるセレクタ(水量 / 速度場 / 浮遊顔料 / 沈着顔料 / 紙ハイト / 湿りオーバーレイなど)。「どのテクスチャをどう可視化するか」を選ぶ表示用シェーダーの分岐 | 「なぜ滲まないのか」を見て診断できる。シェーダーデバッグ困難性への最大の対策 |
| H5 | **ストローク記録・再生** | 入力イベント列(位置・筆圧・時刻)を JSON で記録し、ボタン一発でキャンバスをリセットして同一ストロークを再描画。代表的なテストストロークをリポジトリに同梱 | **同一入力でのA/B比較**が可能に。「手描きし直したら再現しない」を排除。e2e テストの入力にもなる |
| H6 | **シミュレーション制御** | 一時停止 / 1ステップ実行 / 速度倍率 / キャンバスリセット。+ PNG スナップショット | にじみの進行をコマ送りで観察。before/after の証拠を残す |

### CPU参照実装の位置づけ(やりすぎない)

[05](note/05-rust-feasibility.md) §7 の「CPU 参照実装+cargo test」は有効だが、全パイプラインの二重実装は過剰。**GPU の数値が疑わしくなったカーネル単位で後追い実装する**:

- KM 合成と K,S 逆算([03](note/03-layering-glazing-lifting.md) §3)は純粋関数なので CPU 実装+テストで書き、WGSL と突き合わせる(`crates/km`)
- 流体本体は数値の正しさより見た目なので、デバッグ表示(H4)で診断する方が速い
- WGSL はコンパイル可能性(naga)と SimParams のレイアウト一致だけを機械的に守る

## 2. プロジェクト構成

モジュール単位の構成は [architecture.md](architecture.md) §2 が正典。骨格は次のとおり:

```
kasaneiro/
├─ Cargo.toml          [workspace](3 crate)+ kasaneiro package(GPU / UI / 入力)
├─ crates/
│  ├─ km/              Kubelka-Munk 純関数(CPU 参照、cargo test 対象)
│  ├─ pigment/         Palette・mixbox latent / 物性 uniform(mixbox 依存はここだけ)
│  └─ paint-core/      SimParams・Splat・brush・paper・replay モデル・tool(wgpu を持たない CPU 純粋部)
├─ src/
│  ├─ main.rs          eframe 起動
│  ├─ app/             egui UI(PaintApp・パネル群 ui/*.rs・線画履歴)
│  ├─ gpu/             wgpu リソース・パイプライン・フレーム描画(パス実行順)・読み戻し・ホットリロード
│  ├─ input.rs         入力抽象(trait)。マウス / ペン(egui Touch)→ (将来 wasm Pointer)
│  └─ …                プリセット・パレット・色・ストローク・作品の永続化、アセットパス解決
├─ assets/
│  ├─ shaders/*.wgsl   実行時ロード(H1)。通常ビルドは埋め込まない
│  ├─ presets/ palettes/ pigments/ strokes/   JSON(git 管理)
│  └─ fonts/ licenses/
├─ tests/              WGSL コンパイル可能性・SimParams レイアウト検査・e2e
└─ docs/
```

- workspace を km / pigment / paint-core の 3 crate に分けるのは、mixbox 隔離(CC BY-NC)を依存グラフで強制し、CPU 純粋部を wgpu 抜きで数秒テストできるようにするため
- **依存クレートは egui の対応バージョンを起点にロックステップで固定**(egui → egui-wgpu → wgpu → winit の順に合わせる。[05](note/05-rust-feasibility.md) §1 の注意)
- コンパイル時間対策: `[profile.dev.package."*"] opt-level = 2`(依存だけ最適化)+ 自前コードは opt-level 1。シミュレーションは GPU 側なので dev ビルドでも 60fps が出る

主要クレート: wgpu / egui + eframe + egui-wgpu / mixbox / notify(ホットリロード)/ serde + serde_json / image / rfd。筆圧は winit/egui 標準の Touch イベントで取る(octotablet はメッセージループのデッドロック [issue #18](https://github.com/Fuzzyzilla/octotablet/issues/18) で不採用)。

## 3. 先送りする判断(いま決めないことを決める)

| 論点 | 当面の選択 | 再検討のトリガー |
|---|---|---|
| 混色ライブラリ | mixbox クレート(CC BY-NC)。呼び出しは `crates/pigment` に隔離 | 配布・商用化したくなったら自作スペクトラル WGM([02](note/02-pigment-mixing.md) §3)へ差し替え |
| 流体ソルバ | Curtis 簡略版(反復緩和)+**毛細管拡散**(水高さの拡散、[note/07](note/07-capillary-water.md)) | 不安定なら Stam 化、にじみ境界の表情が足りなければ LBM(MoXi) |
| 紙の質感再現(シミュ側) | 既定オフ(paper_amp/gran/wet=0。機構・スライダーは残置) | しばらく使って不要が確定したら紙ハイト機構ごと削除。逆に粒状感が欲しくなったら値を戻すだけ |
| undo(湿レイヤー) | 1段のみ(全面スナップショット)。線画・ハイライトは多段 Undo/Redo(ストローク再生方式) | 水彩側も複数段が欲しくなったら。2048² ではタイル差分化が前提 |
| 線画 Undo の周期チェックポイント | なし(毎回全ストローク再ラスタライズ) | ストローク数が増えて Undo/Redo の再生が体感で遅くなったら(Kストロークごとにテクスチャ退避+差分再生) |
| 同時顔料数(4ch→8ch) | やらない(4ch のまま。色数はパレット・ライブラリ+レイヤーごとパレット記録で実質無制限) | **1つの湿レイヤー内で同時に5色以上を混ぜたくなったら**。やる場合: 浮遊/沈着/乾燥テクスチャを2枚組(2×vec4)にし顔料を触る全シェーダー(約8本)を拡張+ `max_storage_textures_per_shader_stage`(既定4→5必要)を eframe の WgpuConfiguration で引き上げ。512² なら性能余裕、実コストは binding 付け替えの手間 |
| スポイトの意味論 | 表示色を拾う | 「その点の顔料構成」を拾いたくなったら(混合物→単一スロットの写像が曖昧なので沼。表示色版で不満が出てから) |
| 線画のベクター化 | ラスタ(専用テクスチャ) | 線の編集・変形・高解像度書き出しが欲しくなったら。ストローク記録(H5)が生入力を保持しているので後からベクター再構成の余地は残る |
| 下書き鉛筆の境界効果 | なし(清書ペンのみが土手) | 下書き段階で塗りのテストをしたくなったら(鉛筆用の境界強度スライダーを別に足すだけ) |
| ハイライトの水彩シミュ化 | 不透明ブラシ・流体なし | 滲む白(ウェットなガッシュ感)が欲しくなったら。湿レイヤー1枚の現設計に白専用の湿レイヤーを足す大工事なので、不透明版で不満が出てから |
| 線画レイヤーの合成位置 | 色より上・固定(紙→乾燥→湿→線画→ハイライト) | 線を色の下に置きたくなったら(水彩は透明なので当面は上固定で困らないはず) |
| キャンバス形状 | 正方形のみ・サイズ可変(512/1024/2048) | A4 縦長など非正方形が欲しくなったら(キャンバスサイズの width/height 分離、全 dispatch・UI に波及) |
| 高精細化(見た目スケール維持で解像度up) | やらない(2048² は「広い紙」=テクセル密度据え置き) | 同じ絵をより高精細にしたくなったら。拡散の反復 ~16倍・ぼかし半径2乗のコストが出るため、分離ぼかし/SAT・多重解像度拡散などの手当てとセットで |
| WinTab 対応 | やらない(Windows Ink のみ) | 古いドライバのタブレットを使いたくなったら |
| ペンの拡張軸(傾き・ホバー距離・消しゴム検出) | やらない(筆圧のみ。egui Touch 経由) | 傾き等を使うブラシが欲しくなったら octotablet を再評価(ハングバグ issue #18 の修正確認が前提) |
| Web 版 | やらない | 配りたくなったら。input/保存の trait 抽象だけ維持 |
| パス実行の trait 抽象化 | やらない(`encode_frame()` の `run` クロージャが継ぎ目) | dispatch の差し替え方がさらに増えたら、その場で必要な分だけ |
| WGSL の include 機構一般化 | やらない(プレリュード+common.wgsl 連結で足りている) | シェーダー間の共有関数が実際に増えたら |
| GpuCanvas の全面再設計 | やらない(リソース定義が長いだけで責務は一貫) | テクスチャ生成ヘルパー・読み戻しの抽出で不足を感じたら |
| crate のさらなる細分化 | やらない(km / pigment / paint-core の3つまで) | 依存の隔離・純粋性の保証という明確な理由が新たに生まれたら |
